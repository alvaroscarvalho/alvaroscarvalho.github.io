I built an incident war room inside my homelab

September · 2026·6 min read kuberneteshomelabincident-response

1. Why a homelab, and why this one

I've been studying for the CKA, and I learned pretty quickly that managed clusters hide the parts the exam cares about. So I wanted a cluster I could break and rebuild on my own terms: a real kubeadm install, not a single-node toy, running on the laptop I already own.

The second reason is closer to my day job. As an SRE I spend a lot of time thinking about how teams respond to incidents, and 3am is a terrible time to learn your incident process. I wanted a place where I could rehearse a SEV-1 on purpose: pause it, speed it up, replay it. That's where the war room comes in, but it needed a cluster to live on first.

2. The cluster: real kubeadm on a Mac

Everything runs on an Apple Silicon Mac. Multipass spins up three Ubuntu ARM64 VMs: one control plane and two workers. A set of idempotent scripts in bootstrap/ takes care of the boring-but-important bits on each node (swap off, kernel modules, sysctl, containerd with SystemdCgroup), then runs kubeadm init, joins the workers and installs Calico.

make up
export KUBECONFIG=$HOME/.kube/homelab.conf
kubectl get nodes -o wide

Two small decisions I like here. First, the Kubernetes version is deliberately one minor behind the latest, so the very next exercise is a kubeadm upgrade. Second, the pod CIDR is 10.244.0.0/16 instead of Calico's default 192.168.0.0/16, because Multipass on macOS already lives in 192.168.64.0/24 and my home network is in 192.168.x.x too. That one took me a moment to figure out, and it's exactly the kind of thing a managed cluster never teaches you.

3. From hand-written YAML to GitOps

The workloads move through three levels, and each one removes a bit of pain from the previous one:

  1. Everything by hand. Plain manifests and kubectl apply: Deployments, Services, ConfigMaps, RBAC, DaemonSets. Tedious, and honestly the best YAML practice for the exam.
  2. Kustomize and Helm. The same workloads, with overlays and charts instead of copy-paste.
  3. CI/CD and GitOps. GitHub Actions owns the CI (lint, tests, image build, bumping the image tag in Git), and Argo CD runs inside the cluster and pulls from the repo in an app-of-apps pattern. Git is the source of truth, and since Argo pulls instead of being pushed to, nothing outside needs access to my cluster.

The safety net starts on day one: every push runs kubeconform against the manifests, so a typo in a field name fails in CI instead of in the cluster.

4. Monitoring, the hand-rolled way

I skipped kube-prometheus on purpose. It pins everything to a monitoring namespace, and more importantly, writing the stack myself meant writing the RBAC, the DaemonSet and the scrape config myself. So the observability namespace has Prometheus, Grafana, node-exporter and kube-state-metrics, all as plain YAML.

Prometheus discovers targets through the Kubernetes API: the API server, kubelet, cAdvisor, and any pod annotated with prometheus.io/scrape: "true". That last rule matters later, because it means any app I deploy gets scraped with zero extra config.

There are rough edges I left in as homework. Prometheus and Grafana use emptyDir, so data disappears when the pod restarts (moving to PVCs with local-path-provisioner is on the list). And on kubeadm, etcd, the controller-manager and the scheduler only expose metrics on localhost, so they don't show up until you go and fix that.

5. The app: Incident War Room

With a cluster and monitoring in place, I wanted a real app to run on it, something with state, WebSockets and metrics, not another hello-world. So I built a small incident simulator.

You open it in the browser, build a pixel-art avatar, pick a role (Incident Commander, SRE, Network, Backend, Database, Security, PM or Observer) and walk into a 2D war room with a table, wall monitors, a whiteboard and a server rack. Then a scripted scenario starts, like "Production API latency increased to 5s" or an expiring certificate:

  • NPCs fill the empty roles, talk in the chat and raise hypotheses.
  • The simulated metrics (p99 latency, error rate, RPS, CPU, DB connections) degrade and recover as the story moves.
  • The incident follows a real lifecycle: INVESTIGATING → IDENTIFIED → MITIGATING → MONITORING → RESOLVED.
  • Chat commands like /status, /hypothesis, /action and /set-status drive the incident, and everything lands on a timeline.
  • You can pause, restart, or run it anywhere from 0.5x to 10x.

Under the hood it's Spring Boot 3.5 on Java 21, with a React and Canvas 2D frontend (no sprites, everything is drawn in code) talking over REST and a WebSocket. The frontend build is packaged inside the Spring Boot jar, so it's a single container on a single port.

6. Getting it into the cluster, and reaching it through Traefik

I didn't want Docker on the Mac, so the image is built inside a separate Multipass VM called builder, exported, and imported straight into containerd on each worker. No registry involved for local iterations, and the image is ARM64 because the VM is. In the GitOps flow, the same Dockerfile is built by GitHub Actions and published to a registry for Argo CD to roll out.

make k8s-image      # build in the builder VM, import into w1 and w2
kubectl apply -f kubernetes/
kubectl -n incident-warroom rollout status deploy/incident-warroom

The Deployment is where a lot of CKA topics show up in one place: requests and limits, startup, liveness and readiness probes on a separate Actuator port (8081, never exposed by the Ingress), Pod Security restricted (non-root, read-only root filesystem, drop ALL), and a graceful shutdown that closes WebSockets with code 1012 so the browser reconnects on its own during a rollout.

For access, the path is browser → Traefik → Service → Pod. I picked Traefik as the Ingress controller because it proxies WebSockets without any extra annotations, which for a real-time app is the whole point. It's installed with Helm on a NodePort, and I point warroom.local at a worker.

helm install traefik traefik/traefik -n traefik --create-namespace \
  --set service.type=NodePort --set ports.web.nodePort=30080

And because the pod carries the prometheus.io/* annotations, the Prometheus from section 4 picks it up on its own. There's a Grafana dashboard for the app in the repo, so the "fake" incident and the real telemetry of the pod running it sit side by side.

7. What I got out of it

The obvious part is Kubernetes practice. Every deploy of the war room exercises probes, rollouts, security contexts, ingress and scraping, which is basically the CKA syllabus with a reason to care.

The less obvious part is the incident side. Running a scenario over and over made me notice how much of incident response isn't debugging at all: it's who is commanding, who is talking to the business, when the status changes and why. Those are skills you only build by practicing them, and it's a lot nicer to practice them with NPCs than during a real SEV-1.

Next up: moving the app's state from memory to PostgreSQL so it can run more than one replica, persistent storage for Prometheus and Grafana, and new scenarios. If you have a favorite incident you'd like to see turned into one, I'd love to hear it.
